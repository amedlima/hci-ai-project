# User Requirements

## 1. Introduction

This document turns the findings from our [Literature Review](./literature_review.md), [Analysis of Existing Solutions](./analysis_of_existing_solutions.md) and [Secondary User Research Analysis](./secondary_user_research_analysis.md) into clear, testable user requirements for this project.

The literature review explains the research behind human-AI interaction, the existing-solutions analysis shows how current software tools work in practice, and the secondary user research highlights what users currently struggle with when checking AI summaries. This document brings those insights together to define what our prototype needs to do and how we will measure its success during user testing.

## 2. Target Users, Scenarios and Experimental Conditions

To make sure our requirements stay focused on the main problem in this project, they are built around the following users, scenarios and test conditions:

- **Target Users:** Analysts, clerks and managers who delegate heavy document reading tasks (such as credit files, legal contracts, financial statements and administrative records) to an AI agent and are responsible for checking and approving the final result.
- **Scenario A (Summarise a File and Spot Changes from Last Year):** The user asks the AI agent to summarise a client's file and flag anything that does not match last year's record, then checks the summary against the original documents to catch any mistakes.
- **Scenario B (Approve or Reject the Draft with an Audit Trail):** The user checks, edits or rejects claims in the AI agent's draft before it is sent out, completing a clear sign-off step that records who decided what in an audit log.
- **Prototype Conditions to Compare:**
  - **Condition A (Baseline):** A plain AI summary paragraph with no source links, uncertainty notes or claim-by-claim sign-off tools.
  - **Condition B (Source Links and Uncertainty):** An AI summary with clickable source links, highlighted passages in the original document and a confidence/uncertainty note.
  - **Condition C (Our Custom Checking and Sign-Off Design):** A split-screen checking workflow that breaks the summary into separate claims, shows side-by-side source evidence and year-over-year changes, highlights which claims need checking, provides *Approve*, *Edit* and *Reject* buttons for each claim, requires a final human sign-off step and saves a clear audit log.

## 4. Proposed User Requirements and Acceptance Criteria

The requirements below are written as testable statements with clear numerical acceptance criteria (the numbers we will use to judge whether our design succeeded during user testing).

| ID | User requirement (testable statement) | Testable metric | Acceptance criterion (target) | Research references |
|---|---|---|---|---|
| UR-01 | The interface must break the AI summary into separate, individual claims so users can check and spot planted mistakes one claim at a time. | Share of planted errors found (error detection rate) logged in code | Participants catch $\ge 80\%$ of deliberately planted errors in Condition C (and catch more errors than in Condition A). | [Literature Review, Sections 2.2 & 2.5](./literature_review.md#22-fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies); [Factiverse, Section 3.1.1](./analysis_of_existing_solutions.md#311-factiverse); [Pain Point 1](./secondary_user_research_analysis.md#41-pain-point-1-trusting-fluent-ai-answers-too-much-automation-bias). |
| UR-02 | Clicking a source link on any AI claim must immediately scroll to and highlight the matching passage in the original document viewer. | Time taken to find the matching source passage for a claim | Users can jump to and view the highlighted source passage in $\le 3\text{ s}$ per clicked claim. | [Literature Review, Section 2.3](./literature_review.md#23-in-search-of-verifiability-explanations-rarely-enable-complementary-performance-in-ai-advised-decision-making); [Adobe, Section 3.2.1](./analysis_of_existing_solutions.md#321-adobe-acrobat-ai-assistant); [Anara, Section 3.2.5](./analysis_of_existing_solutions.md#325-anara); [Pain Point 2](./secondary_user_research_analysis.md#42-pain-point-2-checking-long-documents-by-hand-is-slow-and-tiring). |
| UR-03 | The interface must clearly label whether each claim is *Supported*, has a *Discrepancy/Contradiction*, or is *Uncertain* based on the source text. | False-rejection rate (wrongly rejecting a correct AI claim) and user accuracy | False-rejection rate of true claims stays $\le 15\%$, while error detection reaches $\ge 80\%$. | [Literature Review, Section 2.2](./literature_review.md#22-fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies); [Factiverse, Section 3.1.1](./analysis_of_existing_solutions.md#311-factiverse); [Scite, Section 3.1.3](./analysis_of_existing_solutions.md#313-scite); [Pain Point 3](./secondary_user_research_analysis.md#43-pain-point-3-missing-contradictions-when-there-are-no-visual-warnings). |
| UR-04 | The interface must show clear uncertainty notes and visual hints pointing out which claims most need human checking. | Share of flagged/uncertain claims inspected by the user (logged via clicks) | Participants click and inspect the source evidence for $\ge 85\%$ of claims flagged as uncertain or conflicting. | [Literature Review, Section 2.4](./literature_review.md#24-im-not-sure-but-examining-the-impact-of-large-language-models-uncertainty-expression-on-user-reliance-and-trust); [Full Fact AI, Section 3.1.2](./analysis_of_existing_solutions.md#312-full-fact-ai); [Spektr, Section 3.3.1](./analysis_of_existing_solutions.md#331-spektr-ai-for-doc-review); [Pain Point 4](./secondary_user_research_analysis.md#44-pain-point-4-not-knowing-when-the-ai-is-guessing-over-trust-vs-under-trust). |
| UR-05 | Users must be able to approve, edit or reject any individual AI claim—and undo a mistake—directly in the summary list. | Time to complete a single claim action or undo a mistake | Users can approve, reject or undo a claim decision in $\le 2\text{ s}$ with $\le 2$ clicks. | [Literature Review, Sections 2.1, 2.6 & 3.1](./literature_review.md#21-guidelines-for-human-ai-interaction); [Full Fact AI, Section 3.1.2](./analysis_of_existing_solutions.md#312-full-fact-ai); [Elicit, Section 3.2.6](./analysis_of_existing_solutions.md#326-elicit); [Pain Point 5](./secondary_user_research_analysis.md#45-pain-point-5-information-overload-and-unclear-responsibility). |
| UR-06 | The interface must help users compare this year's client file with last year's file and spot what changed (Scenario A). | Detection rate of planted year-over-year discrepancies | Participants catch $\ge 80\%$ of planted year-over-year differences between the current and previous year's documents. | [Literature Review, Section 2.2](./literature_review.md#22-fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies); [ABBYY, Section 3.3.2](./analysis_of_existing_solutions.md#332-abbyy-finereader-pdf-document-comparison); [Litera Kira, Section 3.2.4](./analysis_of_existing_solutions.md#324-litera-kira); [Hebbia, Section 3.2.3](./analysis_of_existing_solutions.md#323-hebbia). |
| UR-07 | The system must block final export or sending until the human reviewer completes a clear sign-off step accepting responsibility (Scenario B). | Post-task question on responsibility and sign-off completion rate | $100\%$ of finalised summaries require explicit sign-off; $\ge 90\%$ of participants clearly state who is responsible for the approved summary. | [Literature Review, Sections 2.6, 2.8 & 3.1](./literature_review.md#26-decision-control-and-explanations-in-human-ai-collaboration-improving-user-perceptions-and-compliance); [Spektr, Section 3.3.1](./analysis_of_existing_solutions.md#331-spektr-ai-for-doc-review); [Pain Point 5](./secondary_user_research_analysis.md#45-pain-point-5-information-overload-and-unclear-responsibility). |

| UR-09 | The verification workflow must be easy to use and keep mental effort manageable so checking a document does not feel overwhelming. | System Usability Scale (SUS), NASA-TLX workload score and total task time | Final design (Condition C) achieves a mean $\text{SUS score} \ge 68$ (above average usability) and a mean checking time of $\le 5\text{ minutes}$ per document task. | [Literature Review, Sections 2.6 & 3.3](./literature_review.md#26-decision-control-and-explanations-in-human-ai-collaboration-improving-user-perceptions-and-compliance); [Pain Point 2](./secondary_user_research_analysis.md#42-pain-point-2-checking-long-documents-by-hand-is-slow-and-tiring) & [Pain Point 5](./secondary_user_research_analysis.md#45-pain-point-5-information-overload-and-unclear-responsibility). |

## 5. Safety, Accessibility and Privacy Requirements

In addition to the main features in Section 4, our system must meet the following safety, accessibility and privacy requirements so it is safe, inclusive and ethical to test.

| ID | Category | Requirement statement | Acceptance criterion / verification method | Research & standard references |
|---|---|---|---|---|
| SR-01 | Safety (Preventing Unchecked Sign-Off) | The system must prevent users from approving and sending a final summary while any flagged discrepancy or contradiction claim is still unreviewed. | Attempting to click "Final Sign-Off" with unreviewed discrepancies shows a warning prompt $100\%$ of the time until each flagged claim is resolved. | [Nielsen (1994) Error Prevention, Literature Review, Section 3.1](./literature_review.md#31-nielsens-10-usability-heuristics-for-user-interface-design); [Spektr, Section 3.3.1](./analysis_of_existing_solutions.md#331-spektr-ai-for-doc-review). |
| SR-02 | Accessibility (Visual & Non-Colour Cues) | Status badges (*Supported*, *Discrepancy*, *Uncertain*) and document highlights must never rely on colour alone; they must include distinct icons and text labels with readable contrast. | Text and highlight contrast ratios are $\ge 4.5:1$ (WCAG 2.1 AA), and $100\%$ of status badges pair colour with an icon and text label. | [WCAG 2.1 Level AA, Literature Review, Section 3.2](./literature_review.md#32-web-content-accessibility-guidelines-wcag-21). |
| SR-03 | Accessibility (Standard Laptop & Lab Use) | All core checking, source-jumping and sign-off controls must run smoothly in a standard web browser on an Ubuntu lab computer using only a standard laptop screen, mouse and keyboard. | Prototype installs and runs with zero hardware extras on an Ubuntu lab machine and supports keyboard navigation (`Tab` / `Enter`) for claim review. | [WCAG 2.1 Criterion 2.1.1, Literature Review, Section 3.2](./literature_review.md#32-web-content-accessibility-guidelines-wcag-21). |
| SR-04 | Privacy & Data Protection | Prototype development and user testing must use only made-up (synthetic) client documents, and all logged participant data must be completely anonymised. | $0\%$ real personal or confidential data used; participant logs use anonymous IDs (`P01`–`P10`) with no names, photos or recordings published to GitHub. | [Balakayeva *et al.* (2025), Literature Review, Section 2.8](./literature_review.md#28-an-intelligent-enterprise-system-with-processing-and-verification-of-business-documents-using-big-data-and-ai). |

## 6. Requirements Prioritisation

To keep our project scope realistic for an 8-week schedule, the requirements are grouped into three priority levels:

| Priority | Requirements | Reason |
|---|---|---|
| **Essential (Core Prototype)** | `UR-01`, `UR-02`, `UR-03`, `UR-05`, `UR-07`, `UR-08`, `SR-01`–`SR-04` | Needed to run our user study comparing Conditions A, B and C: claim breakdown, source links, status badges, accept/reject buttons, human sign-off and automatic audit logging. |
| **Important (Target Polish)** | `UR-04`, `UR-06`, `UR-09` | Needed to support Scenario A (flagging changes from last year), checking hints for uncertain claims and meeting our usability/workload targets. |
| **Stretch (Optional Extra)** |Dedicated side-by-side "what changed since last time" diff view | Enhances Scenario A if time allows after the core study conditions and automatic logging are working and tested. |
